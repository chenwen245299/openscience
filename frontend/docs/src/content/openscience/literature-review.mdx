## Define the question

Give OpenScience a question, date range, sources, and inclusion criteria. Start in plan mode if those choices are not settled.

```text
/plan Review protein language models for predicting mutation effects.
Cover work published since 2022. Include experimental validation and
separate preprints from peer-reviewed papers. Propose the search terms
and inclusion criteria before searching.
```

A broad request such as "find everything about cancer" is hard to verify. Narrow it to an organism, method, outcome, or comparison.

## Search and collect evidence

After reviewing the plan, ask OpenScience to search and save a source table:

```text
Run the agreed search. Save results/sources.csv with title, authors,
year, DOI or source URL, publication status, method, dataset, and the
reason each paper was included. Record the search date and queries.
```

Available literature databases include PubMed, Europe PMC, arXiv, bioRxiv/medRxiv, OpenAlex, Crossref, and Semantic Scholar. The [database directory](/openscience/databases) lists the built-in sources.

Search access and full-text access are different. A title or abstract result does not mean the full paper was read. Ask OpenScience to identify abstract-only evidence and inaccessible sources explicitly.

## How papers are found and read

The `literature` tool is the agent's default path to papers.

- **Search** runs one query against OpenAlex and arXiv together, merges records that describe the same paper (by DOI, arXiv id, or title), and ranks papers both sources agree on first. Each candidate carries the DOI or arXiv id, venue, citation count, abstract, landing page, and whether an open full text exists. The result says which source answered, which answered through a fallback, and which failed. Other connectors (`pubmed`, `europepmc`, `biorxiv`, `crossref`, `semantic-scholar`) can be named with `sources`.
- **Read** takes a DOI, arXiv id, URL, local PDF, or exact title, resolves the open full text (arXiv PDFs directly, publisher and repository copies through OpenAlex's open-access locations), downloads it once into the session's paper cache, and extracts page-addressed text with `pdftotext` (poppler) or PyMuPDF. The agent reads the opening pages, a page range, or the passages matching a phrase, each tagged with its page number. When only the abstract is open, the result says so instead of pretending to have read the paper.

The cache lives in the session's scratch workspace under `papers/`, so re-reading a paper costs nothing and survives across turns.

For a molecular design run, the agent calls `literature` with `action: "read"`, the `run` directory and a retained paper's `source` (DOI, arXiv id or exact title). The built-in interface resolves Europe PMC body XML, arXiv HTML/PDF and open-access copies, saves complete section/page-addressed evidence in the run, and updates the paper record. It reuses saved bodies for further `query` or `pages` calls and accepts a supplied local PDF via `ref`. The agent does not need to discover API endpoints, write download scripts or reconstruct evidence files. Inaccessible bodies remain unavailable. Retrieval supplies the evidence; the agent reads it and writes the supported design takeaways.

### When arXiv rate limits

arXiv's API answers bursts of requests with `429` for a while, often after a long stall. OpenScience now treats one such answer as a signal: the API is held for a cooldown (a minute, doubling on repeats) and arXiv records are served from OpenAlex, which indexes every arXiv paper under `10.48550/arXiv.<id>`, or from the paper's own `arxiv.org/abs` page. Results obtained this way are marked `via`. If every route fails, the error reports the HTTP status, the endpoint, the number of attempts, and any requested wait, together with the concrete alternatives, so the agent can choose a different source instead of retrying the same call.

Text extraction needs `pdftotext` (macOS: `brew install poppler`; Debian and Ubuntu: `apt-get install poppler-utils`) or the `pymupdf` Python package. Without either, the PDF is still downloaded and the agent can open it with the `read` tool.

## Compare findings

```text
Group the included papers by evaluation method. Compare datasets,
baselines, reported metrics, and failure cases. Cite a source for every
numerical claim and distinguish author claims from your interpretation.
```

OpenScience can synthesize the material it retrieves, but a polished summary can still contain errors. Check the most important claims against the linked source.

## Save a review packet

Ask for a report, a source table, and a bibliography. Keep excluded papers and their reasons when the workflow requires a reproducible screening record.

Suggested outputs:

| File | Contents |
| --- | --- |
| `results/review.md` | Findings, disagreements, limitations, and open questions. |
| `results/sources.csv` | Included sources and extracted evidence. |
| `results/references.bib` | Bibliographic records you have checked. |
| `results/search-methods.md` | Queries, sources, dates, and inclusion criteria. |

These are requested deliverables, not automatic outputs of every search.

### Molecular design runs

For a MolAgent molecular design run, open **Design run** in the right panel. Click a step heading to collapse or expand the whole step. Each step shows its key results: literature sources and paper selection counts; database retrieval and filtering counts; then the generation method and shortlist. Collapsing a step preserves the expanded lists inside it, including during refreshes.

Completed steps have a solid green circle with a bold white check. Unfinished steps have hollow circles; the status text distinguishes running, pending, and failed steps.

Results remain available after the run finishes. Reopening the panel or returning to the session restores its saved runs and step outputs. When a session has multiple output directories, use **Design runs** at the top to switch between runs, including an earlier full pipeline and a later design-only round. Existing results are also recovered from the session workspace and its chosen working folder.

**Not kept** results are grey, including their titles and recorded reasons. **Literature output** has two views: **Papers** and **Findings**. Papers appear as numbered cards with titles, years, saved search sources and screening reasons; each says whether its body was read, saved for review, unavailable or outside the priority batch. Saved numerical data, including older runs' abstract extractions, remain in expandable **Supporting evidence** inside the corresponding paper card. Excerpts with no unambiguous source stay separately labelled as unlinked paper evidence.

**Findings answers “how should we design next?”** Each takeaway is a design principle, precaution or technique learned from reading the paper bodies. It states the recommended action, why it is supported, relevant conditions/trade-offs and how to use it in database retrieval/filtering or subsequent molecular modification. Each has a clickable **Supporting paper**, available DOI/year, the literal supporting excerpt and section/page; a direct body link appears when available. Raw numbers and mechanically selected passages do not count as design takeaways. While body review is pending, the panel says the agent is still reading and summarizing.

Each view preserves its scroll position and expanded details while switching or refreshing. Molecular outputs expand to show the top candidates and next validation steps; three candidates appear initially, with the rest expandable. PubChem and RDKit have logos beside the source/tool names used in the run.

Sources have their own logos. Click a source's **hits** count to expand its results by query, including titles, years when available, and links. Hit counts include repeated records across queries; the paper-selection summary reports the deduplicated count. Results and expanded lists stay in place while the run refreshes. Older runs that saved only counts show a notice instead of invented hit details.

Paper selection is a relevance ranking, and abstract data still need full-text verification. Older runs may not have saved the excluded paper details. Molecular scores are structural estimates; candidates retained as a fallback after failing checks are marked for review.

Each retained paper shows **Why kept**, and each molecule in Steps 2 and 3 shows **Why shortlisted**. Expand **Selection details** for the supporting record. New literature runs save all matched topic concepts, title/abstract matches and excerpts, score contributions, and rank. Database runs record the rank before diversity filtering and the measured similarity to earlier selections. Design runs record the eligible-pool rank and synthetic accessibility (SA) filter, along with the saved design intent, parent, and ranking-score change when available. Exact structural checks distinguish passed requirements from unmet preferences; fallback selections and unavailable SA scores are identified explicitly. Logos in all three steps use transparent backgrounds.

Older runs show their recorded reasons, checks, and design metadata. Saved goal concepts can reveal title and abstract matches, labelled as saved metadata rather than a reconstructed screening decision. Missing ranking, diversity, or SA thresholds are not invented. Design intentions and scores describe why a candidate was proposed or shortlisted; they do not establish measured molecular performance.

Step 1 retrieves important open paper bodies, saves addressed passages and returns control to the research agent for interpretation. **Reviewing literature** means the agent is reading and synthesizing evidence; this is not an approval request. The agent checks relevant structures, results, conditions and limitations, then resumes the same run with a source-backed review. Unavailable bodies remain visible and can be retrieved through the literature tool or supplied as local papers.

Step 2 reads the reviewed EvidencePack alongside the GoalSpec and supplied seed structures. All takeaways, including precautions and techniques, carry into Steps 2 and 3 with their supporting citations under **Design guidance**. Preferred supported molecular motifs generate PubChem substructure searches; reviewed prefer/avoid features add bounded soft ranking preferences. The panel separately shows the finding IDs used by automatic ranking and literature-derived queries, and candidates record the corresponding matches. Step 3 uses the same literature preference term when comparing designs with their parents. Structural hard checks remain separate. Nanoparticle/formulation-specific results and measured values do not automatically become single-molecule filters or screening thresholds. Takeaways outside the automatic structural vocabulary remain available to the agent for selecting structures and planning modifications, with evidence gaps recorded explicitly.

## Revisit the review

Reopen the session, refer to the saved source table, and state the new cutoff date. Ask it to report additions and changes instead of silently replacing earlier conclusions.

For a formal systematic review, agree on the applicable screening and reporting process with your team. OpenScience can assist with the work; a search alone does not establish completeness.
